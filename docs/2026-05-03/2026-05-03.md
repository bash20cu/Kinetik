# Plan de mejora técnica + login con password simple

## Resumen
Vamos a priorizar estabilidad del dominio, seguridad básica real y mejor trazabilidad operativa antes de seguir ampliando UX. El cambio más importante será reemplazar el login actual por “email libre sin verificación” por un acceso con `email + password`, sin reglas estrictas de complejidad por ahora, y con creación de cuentas solo por administrador.

## Cambios clave
- Autenticación y sesiones:
  - Reemplazar `signInWithEmail` por flujo de `signInWithPassword`.
  - Agregar `passwordHash` al modelo `User`; nunca guardar passwords en texto plano.
  - Crear una forma de provisionar usuarios por admin fuera del registro público.
  - Eliminar registro implícito al hacer login; si el usuario no existe, devolver error controlado.
  - Hacer que el estado “app configurada” exija `DATABASE_URL` y `SESSION_SECRET`.
  - Mantener cookie de sesión, pero limpiar sesiones inválidas y centralizar validación de secret/configuración.
  - Añadir logout y mensajes de error de login consistentes en UI.
- Modelo de acceso:
  - No habrá pantalla pública de “crear cuenta”.
  - La creación de usuarios quedará resuelta por una vía administrativa simple:
    - primera opción: script/seed local para crear usuario con password hash.
    - dejar preparado el código para luego moverlo a panel admin si hace falta.
- Robustez de acciones y datos:
  - Validar `FormData` y payloads JSON con esquema explícito antes de persistir.
  - En `saveSession`, validar enums permitidos y normalizar numéricos antes de escribir.
  - En importación CSV, envolver el flujo completo para que `PlanImport` termine siempre en `success` o `failed`, nunca en `processing` colgado.
  - Hacer que `getUnreadAlerts` filtre `readAt: null`.
- Sesiones de entrenamiento:
  - Evitar sesiones duplicadas por `user + day + fecha`.
  - Al crear sesión, si ya existe una del mismo día, reutilizarla en lugar de crear otra.
  - Añadir restricción de base de datos para reforzar esa unicidad.
- Fechas y consistencia:
  - Centralizar helpers de fecha para evitar mezclar `new Date()` local con `toISOString().slice(0, 10)` disperso.
  - Definir una sola política para fechas de negocio:
    - `sessionDate` y `activeFrom` se calculan en zona de negocio consistente.
  - Ajustar calendario semanal y asignación de “hoy” para que no dependan accidentalmente de la zona del servidor.

## APIs, tipos e interfaces
- Prisma:
  - `User.passwordHash` nuevo campo obligatorio para cuentas activas.
  - índice o restricción única para `WorkoutSession` por combinación de usuario, día y fecha.
- Server Actions:
  - `loginAction` pasará a recibir `email` y `password`.
  - se elimina la creación automática de usuario desde el login.
- UI:
  - [app/login/page.tsx](/home/migue/Documentos/proyectos/github/Kinetik/app/login/page.tsx) mostrará campo de password y errores legibles.
  - no se agrega pantalla de signup público.
- Operación:
  - agregar script documentado para crear usuarios admin-managed, por ejemplo `npm run user:create`.

## Pruebas y escenarios
- Auth:
  - login correcto con credenciales válidas.
  - rechazo con email inexistente.
  - rechazo con password incorrecto.
  - app sin `SESSION_SECRET` no debe mostrar login operativo ni fallar tarde.
- Sesiones:
  - doble submit en “crear sesión” no genera duplicados.
  - si ya existe sesión del día, el usuario vuelve a esa misma sesión.
- Alertas:
  - solo se listan no leídas en dashboard.
- Importación:
  - CSV inválido marca `PlanImport.failed` con resumen.
  - fallo inesperado durante importación no deja registros en `processing`.
- Fechas:
  - “hoy”, semana actual y fechas guardadas se comportan igual en local y deploy.

## Orden recomendado
1. Endurecer configuración y login.
2. Agregar password hash + migración + script de creación de usuarios.
3. Validar Server Actions y entradas críticas.
4. Corregir duplicados de sesión y restricción en DB.
5. Arreglar alertas no leídas.
6. Unificar manejo de fechas.
7. Añadir tests mínimos de auth, sesiones e importación.

## Supuestos y decisiones
- Sí se agrega password, pero sin reglas estrictas de complejidad en esta etapa.
- No habrá registro público.
- Las cuentas las crea solo un admin/manualmente.
- La app sigue orientada a pocos usuarios conocidos, no a apertura pública.
- No se abordará en esta fase recuperación de password por email ni MFA.
